## Context

APCS 中級題本的能力指標是「以序列型資料結構儲存與處理資料」，檢測範圍為陣列、字元、字串。掃過本站現有 17 道 apcs 題的 generator 後，技法分佈是：單趟掃描模擬 17 題、排序 1 題、二維陣列 0 題、前綴和／差分 0 題、雙指標／滑動視窗 0 題、頻率表計數 0 題。中級真正的核心（先把資料存進陣列、再回頭整體處理）沒有任何一題在練。

平台已具備兩道效率閘門，本 change 三題全部倚賴它們：

| 閘門 | 值 | 出處 |
|---|---|---|
| 單筆測資 wall-clock deadline | 5000 ms | `openspec/specs/judge-deadline/spec.md` |
| 單筆測資運算次數上限 | 10,000,000 ops | `openspec/specs/counting-trio-challenges/spec.md` |
| 單筆測資輸入位元組硬上限 | 65536（不可覆寫） | `Usage.md`〈輸入規模預算〉 |

前例 apcs015 的暴力路線消耗 216,759,740 ops 被運算上限砍死、得 8/20，證明斷崖是可設計且可量測的；而它的死因是運算上限而非 wall-clock，本 change 三題的斷崖也一律以運算次數為準來估算。

輸入位元組硬上限是三題規模的真正約束：所有的 N、F、K 上界都是從 65536 反推出來的，不是先選一個好看的數字再去湊。

## Goals / Non-Goals

**Goals:**

- 三題各補一個現有題庫完全空白的技法：二維差分、排序後維護狀態、固定視窗加頻率表
- 三題都設效率斷崖，暴力解在小測資拿部分分、在大測資被運算上限砍死，讓「為什麼要學這個技法」有可驗證的答案
- 三題的輸出在本站的逐字比對判題下唯一，不依賴 special judge
- 三題的輸入設計完全繞開測資引擎的既有限制，不修改 Rust crate

**Non-Goals:**

- 不修改 crate `testcase-generator`。引擎不支援「參數值域引用其他參數」，三題一律繞開。
- 不出中高級題型（遞迴、樹、圖、搜尋）。
- 不新增教學文章。
- 不發 release，只做到 merge 進 `staging`。

## Decisions

### 三題的輸入一律採欄位式，不用 group

測資引擎的 `count` 只能在同一行產生**同值域**的多個值，而 `group` 內每個參數各佔一行（`Usage.md`〈count — 產生多個值〉與〈group 群組〉）。因此「每筆紀錄一行、行內多個不同值域的數」做不出來。

改採欄位式：同一個欄位的 N 個值排成一行，用 `count: { from: <前面宣告的 int 參數>, separator: " " }`。這是既有題目 `print-farm-schedule` 與 `pillbox-reminder` 已在用的寫法，不是新機制。

被否決的替代方案：（一）每筆紀錄拆成多行的 group，可行但把單筆紀錄切散、題面難敘述；（二）擴充 Rust 引擎支援相依值域，成本遠高於三道題的價值，且會讓本 change 同時動到測資引擎與題目內容兩個子系統。

### A 題的矩形以「起點加長寬」表達，越界由測資分區的一致性規則保證

矩形若以「兩個角落」輸入，引擎會產出右下角在左上角之前的無效矩形，而值域無法互相引用、擋不住。改以左上角座標加上高與寬，兩者都是獨立常數值域，天然合法。

越界則靠 `testcase_plan` 每一筆 override 的一致性保證：**每一筆的 override 都必須滿足 `r_max + h_max − 1 ≤ R` 且 `c_max + w_max − 1 ≤ C`**。題面因此可以寫「風域保證完全落在地板範圍內」，不需要定義邊界裁切規則。

這條一致性規則是本題最容易在後續維護中被破壞的地方——調整任何一筆的 `f`、`hs`、`ws` 或 `rc` 都可能讓它失效，而失效的症狀是測資悄悄產生越界矩形、generator 與 reference_solution 仍然一致（兩邊都用同一份輸入），守門測試不會叫。因此它必須有獨立的驗收動作，見〈Implementation Contract〉。

被否決的替代方案：題面規定越界部分被牆擋住、自動裁切。它讓所有 override 組合都合法、消除上述維護風險，但多一條與演算法無關的規則要敘述，且使用者在需求討論時明確選擇了「保證不越界」的版本。

### 運算計數器對 C 層的工作是瞎的，斷崖必須以最便宜的拼法背書

本 change 的第一版把三題的斷崖算在「暴力路線的迴圈拼法」上，經實測全部站不住。判題器的運算計數器（`.vitepress/theme/workers/worker-utils.ts` 的 tracer）計的是**執行的 trace event 數**，也就是 Python 層的行事件。任何把工作推進 C 內建（切片指定、`set()`、`Counter`、`sorted`）的拼法，不論處理多少元素，都只記下**一個** event。

實測（每個抽樣都跑過，數字見 `measure/cliff-spellings.json`）：

| 題 | 同一條被砍路線的兩種拼法 | 每元素計數 | 第 20 筆 ops |
|---|---|---|---|
| A | 巢狀迴圈 `grid[r][c] += 1` | 約 2.04 | 10,551,617（死，只超 5%）|
| A | 切片 `row[a:b] = [x + 1 for x in row[a:b]]` | 約 1.06 | 5,462,719（**活**）|
| C（原設計） | 逐元素迴圈 | 約 3 | 10,000,001（死）|
| C（原設計） | `len(set(songs[s:s+k])) == k` | 約 0（與 K 無關）| 17,392（**活，差 578 倍**）|

wall-clock 也救不了：C 題那條 C 拼法在 CPython 只花 0.062 秒，離 5000 ms 有兩個數量級。

計數器還對第二件事是瞎的：**原始碼的排版**。把迴圈本體折到 `while` 或 `for` 那一行，每次迭代的計數就從三個變成一個，而程式一點也沒變快。C 題的折行變體因此在瀏覽器連續三次拿到 20/20、19/20、20/20。平台其實早就知道這件事——`openspec/specs/judge-deadline/spec.md` 明寫 enforcement 不得依賴運算計數器，並把「把迴圈迭代壓成單一行」列為具名 scenario，交給 wall-clock deadline 處理。

**本機的運算計數是代理指標，不是分數。** 它在本 change 裡兩度給出被瀏覽器推翻的結論。所有分數一律以 `pnpm preview:cf`（Cloudflare 本機執行環境，COOP／COEP 齊全、SharedArrayBuffer 可用、deadline 真正生效）的實測為準，記錄在 `measure/browser-cliff.json`。

**凍結後的標準**（不得再往上加，除非三題全部重測）：

1. `reference_solution` 得 20/20
2. 最直觀寫法的暴力解得 1/20 到 19/20
3. 與某個已死拼法**只差排版**的變體，同樣得 1/20 到 19/20

第 3 條是獨立的一條，因為它是唯一擋得住「純排版就滿分」的門檻，而且做得到——C 題把值域從 10⁶ 提到 4×10⁶ 之後，折行變體三次重測為 15/20、16/20、15/20。

**把工作推進 C 內建的拼法則接受為另一條滿分路線，記錄但不追殺。** 實測有兩條存活：A 題的 `map(operator.add, …)` 得 20/20（最慢 1448 ms）、B 題的 `itertools.compress` 得 20/20（最慢 788 ms）。追殺不成立的理由是算出來的：65536 位元組上限把 B 的比較對數封在約 2650 萬、把 A 的格數封在約 2280 萬，最大可行成長仍讓它們停在 5000 ms deadline 之內；而為了加大工作量去放大地板格數，反而會把正解本身推向 deadline（正解成本就是格數）。同一種接受在 `gem-blast-challenge` 已有前例。

教學上真正重要的分界是：**學生第一次會寫出來的每一種寫法都拿部分分**（巢狀迴圈、平鋪的 for 掃描、延伸到撞重複的迴圈），而存活的那兩條需要對 `itertools` 與 `operator` 有刻意的熟練度。

被否決的替代方案：繼續加大規模直到 C 內建拼法也死。算過不可行（見上），而且這正是本專案流程守則點名的失敗模式——標尺逐輪升高，收斂目標不斷後退。

### A 題的規模由「最便宜的暴力拼法必須死」反推，地板固定為 300×300 格點

暴力路線是逐台吊扇把矩形內每一格加一，成本是所有矩形面積的總和 `cells`。門檻由**切片拼法**（約 1.06 計數／格）決定，不是巢狀迴圈拼法：要它超過一千萬，需要 `cells` 大於約 943 萬。

- 風域高寬各取 `[1, 150]`，平均面積約 75.5² ≈ 5700 格
- 吊扇數 F 上界 3000 → `cells` 約 1710 萬
  - 切片拼法約 1810 萬 ops，**死**（超出 81%）
  - 巢狀迴圈拼法約 3490 萬 ops，**死**（超出 249%）
- 左上角座標取 `[1, 151]`，因此 151 + 150 − 1 = 300 = R，風域永遠落在地板內
- 地板 300×300 = 90000 格；正解建差分表加二維前綴累加約 18 萬步，**過**
- 輸入量：4 個欄位各 3000 個數，每數 4 bytes → 約 48000 bytes，在 65536 之內

地板 300×300 對應每格約 10 公分見方、30 公尺見方的禮堂，情境上站得住。

兩種拼法的死亡門檻不同（巢狀在 F 約 860 就死、切片要到 F 約 1654），所以階梯中段會有一段區間是「巢狀死、切片活」。這無法消除，也不需要消除——階梯頂端兩者都死，兩種拼法的得分都落在部分分區間。兩者的實測得分都要記進量測記錄。

**已知且接受的中間路線**：逐列做一維差分（對每台吊扇的每一列各做兩次標記）成本是 O(F·h + RC) ≈ 32 萬步，會通過。這是正當的差分思路，接受為滿分解。斷崖切在「純暴力填格」與「任何形式的差分」之間，這正是本題要教的分界。

### B 題以「編號最小的空教室」規則讓輸出唯一

CSES 1164 的合法分配有很多種，原題用 special judge 接受任意一種。本站判題是逐字比對 generator 的期望輸出，沒有 special judge，照原題出會把正確解判錯。

因此加入行政規則：處理順序為開始時間由早到晚、同時開始者依申請編號由小到大；每筆申請發給「當下空著的教室中編號最小的一間」，全滿則新開一間。因為永遠取最小空號，已開教室的編號集合恆為 1 到 K 的連續前綴，新開的一間編號即為 K+1，規則自洽。

被否決的替代方案：（一）只輸出最少教室數，輸出唯一但題目退化成同時人數峰值，而該問題在小時間值域下可用一維差分解，與 A 題技法重疊；（二）規則改成「最晚空出來的教室」，輸出同樣唯一且不需要優先佇列，但規則的行政合理性較弱。

### B 題的斷崖切在 O(N²) 與 O(N·K) 之間，heapq 是優解而非必要

需求討論時的預期是本題會強迫使用 `heapq`。細算參數後這個預期**不成立**，理由記錄如下，避免後續維護者為了「讓 heapq 變成必要」而去調大測資規模。

最少教室數 K 就是最大同時使用數，而它的期望值約為 N × 平均借用時長 ÷ 時間軸長度。要讓「逐間掃過所有已開教室找最小空號」的 O(N·K) 路線超過運算上限，需要 N·K 大於約一千萬；在位元組上限允許的 N 之下，這要求 K 是數百到上千間教室同時在用。任何「學校借教室」的情境都撐不住這個數字。

因此本題採用情境上合理的參數：時間軸為一週共 10080 分鐘、開始時間取 `[1, 9000]`、借用時長取 `[30, 105]` 分鐘（半小時到一小時三刻），N 上界 6000。

**期望值不是答案。** 上述參數的平均同時使用數約為 6000 × 67.5 ÷ 9000 ≈ 45，但題目要的是**最大**同時使用數，以引擎實際產出的池（seed 為 slug、10 個 block）逐一量測第 20 筆（N = 6000），得到 64、65、65、71、67、67、64、71、72、68，區間為 64 到 72 間（量測記錄見 `measure/cliff-club-room-allocation.json`）——本 change 的第一版把這兩個量搞混，在規格裡寫下「約 60 間」而實際是 82 到 89 間（當時 N 為 4000、時長上界 240）。規格裡任何關於教室數的敘述一律以實測值為準，不得由期望值推導。

斷崖的門檻由**集合生成式拼法**決定，不是逐行迴圈拼法：`{room[j] for j in range(i) if end[j] > s[i]}` 每比較一對只記約 1 個計數，而展開的 for 迴圈記約 2 個。以最便宜的拼法計，N 要大於約 4472 才會超過一千萬，這正是 N 上界從 4000 提高到 6000 的原因。

- **死**：對每筆申請掃過所有先前申請判斷時間重疊
  - 集合生成式拼法，N = 6000 → 約 1800 萬 ops（超出 80%）
  - 逐行迴圈拼法，N = 6000 → 約 3600 萬 ops
- **過**：排序後只維護每間教室的最後結束時間、逐間找最小空號，O(N·K) ≈ 40 萬步
- **過**：排序後用 `heapq` 維護，O(N log N) ≈ 8 萬步

輸入量：開始分鐘每數 5 bytes、借用時長每數 4 bytes，N = 6000 → 約 54000 bytes，在 65536 之內。

這仍然是本題要教的東西——**先排序、只維護教室狀態，而不是每次都回頭翻所有紀錄**——並且完全落在 APCS 中級的「陣列加排序」範圍內。`heapq` 成為一條額外的優解路線，作為往中高級的搭橋，但不是通關的門檻。難度仍標 hard，理由是規則層數（排序、同時開始的 tie-break、最小空號、新開編號）與雙段輸出，不是漸近複雜度。

### C 題改問「最長不重播段」，因為固定視窗問法在這個平台上殺不掉

第一版的問法是「長度 K 的連續段有幾段完全不重播」。它在這個平台上**無法成立**，而且不是調參數能救的：

暴力路線「每段各自去重」的最便宜拼法是 `len(set(songs[s:s+k])) == k`。整段去重發生在 C 內部，計數器只記約 3 個 event，**與 K 完全無關**：實測第 20 筆（N = 7000、K = 1000）只花 17,392 ops，離一千萬差 578 倍。要靠 wall-clock 擋也不行——同一筆在 CPython 只跑 0.062 秒。而位元組上限把 N×K 封在約 2450 萬個 C 層元素操作，換算約 1.2 秒，連 5000 ms 的一半都不到。**沒有任何規模設定能砍掉它。**

更糟的是教學訊號會反轉：寫一行 `set` 的學生拿 20/20，老實展開迴圈的學生拿 16/20。

因此問法改為：**這份點播序列裡，最長的一段連續不重播有多長。** 情境不變（廣播社要剪一條接力帶，希望愈長愈好、整條不能有重複的歌），slug 與 id 都不動。

這個問法對 C 內建拼法免疫，理由是結構性的：暴力路線「從每個起點往右延伸到撞見重複為止」的內層是**資料相依的提早跳出**，無法表達成對某個固定切片呼叫一次 C 內建。任何想用 `set()` 的拼法都必須自己控制延伸長度，那個控制迴圈就在 Python 層。

參數：N 上界 7000、歌曲編號值域 `[1, 4000000]`，不再需要 K 參數（連帶消除了第一版「每筆都必須滿足 K 不超過 N」的維護風險）。

- 值域必須大：隨機序列中從任一起點能延伸的長度期望值約為 √(2S) ≈ 2828，暴力成本才會是 N × 2828 這個量級。若把編號縮成小字母表，延伸長度被種類數封頂，暴力退化成線性而過關。
- **值域不得降回 10⁶**：那時折行變體三次重測為 20/20、19/20、20/20，最慢一筆落在 4249 至 4519 ms，貼著 5000 ms deadline 擲骰子。提到 4×10⁶ 不花任何輸入位元組（兩個上界都是 7 位），卻把該變體移到 15/20、16/20、15/20。
- **死（實測）**：逐起點延伸的迴圈 14/20；同一段折行 15、16、15/20；逐起點二分搜尋配 `len(set(切片))` 16/20
- **過（實測）**：雙指標配「每首歌上次出現的位置」20/20，最慢一筆 15 ms
- 輸入量：7000 個 7 位數加分隔約 56000 bytes，在 65536 之內

**二分搜尋路線在值域提高後也只拿部分分**：對每個起點用二分搜尋配 `len(set(切片))` 判斷（延伸長度具單調性，所以二分正確），實測 16/20、最慢一筆 5005 ms。值域還是 10⁶ 時它是 20/20；提高之後連它也落進部分分區間。規格因此不再把它描述為滿分路線。

### 三題共用階梯式測資分區，第一筆為題面範例

`testcase_plan` 各 20 筆。第 1 筆用 `literal` 寫死，內容與題面範例逐字相同，讓學生第一筆就能對照。第 2 到第 20 筆用 `count` 加 `override`，規模由小到大平滑爬升，暴力解自然死在中段而不是全滅，得分為部分分。形狀沿用 apcs015 的階梯（N 依序 1, 2, 3, 4, 6, 21, 72, 249, …）。

被否決的替代方案：兩段式（前 8 筆小、後 12 筆直接拉到上限）。邊界最明確、驗證成本最低，但學生得不到「逐步變慢」的手感，部分分的診斷價值下降。

### 說明圖沿用 apcs013／apcs014 的既有管線

每題一張圖，`scripts/figures/<slug>_plate.py` 產出 HTML、`scripts/figures/<slug>_plate.sh` 以 headless Chrome 轉 PNG、輸出到 `docs/public/assets/challenge/<id>/圖一.png`。

**缺圖是建置失敗，不是破圖。** 題面寫下 `![…](/assets/challenge/<id>/圖一.png)` 之後，若檔案不存在，Vite 會在打包時解析不到該匯入而讓 rollup 直接中止，訊息是 `Rollup failed to resolve import`，`pnpm docs:build` 以 exit 1 收場。本 change 的三位審查者都把缺圖判成「頁面會渲染破圖」的 minor 問題，實際上它擋住整條建置線。任何「先寫題面、圖之後補」的排程都必須知道這件事：在圖產出前，這個 change 是建不起來的。

管線的硬限制照抄 apcs013 的既有結論，不重新推導：題目說明面板在 1728 px 桌機上量到的欄寬是 643 CSS px，因此畫布一律 1280 px 寬、直式，顯示時剛好 2 倍；任何字級不得低於 24 authored px（螢幕上 12 px）。字型取自 `.claude/skills/canvas-design/canvas-fonts`，該目錄走 Git LFS，重建圖前需要先 `git lfs pull`。

三張圖各自要畫的東西：

- `hall-fan-coverage`：地板格點加三台吊扇的風域矩形，重疊處標出被加了幾次；旁邊畫出差分的四角標記與還原後的結果
- `club-room-allocation`：時間軸上的借用區間甘特圖，標出每筆被分到的教室編號，以及某一間教室被釋放後立刻被下一筆取用的那一刻
- `radio-relay-tape`：一維點播序列加一段最長的不重播區間，畫出雙指標右端往前推、撞見重複時左端如何跳到「上次出現位置的下一格」

### reference_solution 與 generator 必須是不同寫法

三題都宣告 `reference_solution`，讓 `scripts/content-regression.test.ts` 驗證正解在正式加密池下與 generator 一致。兩者刻意用不同的實作路線（例如 A 題 generator 用二維差分、reference_solution 用逐列一維差分），才能同時抓出兩邊各自的錯誤；若兩份程式碼是同一套邏輯的改寫，這個守門就退化成自我確認。

## Implementation Contract

**行為**：三個新題目頁上線後，學生在 `/apcs-challenges` 看得到三道新題，各自可作答、可提交、可得到 0 到 20 分的判定；每題的題目說明面板內含一張說明圖。

**資料形狀**：

- `hall-fan-coverage`（id 由 scaffold 配發，預期 apcs018）
  - 輸入：第一行兩個整數 R C；第二行一個整數 F；接著四行，各 F 個以單一空白分隔的整數，依序為每台吊扇風域左上角的列、左上角的行、高、寬
  - 輸出：一行一個整數，被最多台吊扇吹到的那一格所被吹到的台數
- `club-room-allocation`（預期 apcs019）
  - 輸入：第一行一個整數 N；第二行 N 個以單一空白分隔的整數，為每筆申請的開始分鐘；第三行 N 個整數，為每筆申請的借用時長（分鐘）
  - 輸出：第一行一個整數，最少要開的教室數；第二行 N 個以單一空白分隔的整數，第 i 個為第 i 筆申請（依輸入順序，非排序後順序）分到的教室編號
- `radio-relay-tape`（預期 apcs020）
  - 輸入：第一行一個整數 N；第二行 N 個以單一空白分隔的整數，為點播序列的歌曲編號
  - 輸出：一行一個整數，最長的一段連續且歌曲兩兩相異的區段長度

**失敗模式**：

- 建置期若單筆測資的 worst-case 位元組估算超過 `input_budget`，`pnpm build:pools` 直接失敗並列出逐參數估算式。三題的 `input_budget` 由 4096 調高，但一律宣告在 65536 硬上限之下。
- 若任一題宣告了引擎不認識的型別或欄位，`scripts/challenge-params.test.ts` 會指名該題失敗。
- 若 `reference_solution` 與 `generator` 的輸出不一致，`scripts/content-regression.test.ts` 會失敗（本機無 python3 時該測試會 skip，因此不能只靠本機綠燈就宣稱通過）。
- 若題面數學記號違反黑名單，`scripts/latex-notation.test.ts` 會指名該行失敗。

**驗收條件**：

1. `pnpm typecheck`、`pnpm lint`、`node_modules/.bin/vitest --run` 全數通過，且 `content-regression` 確實有執行而非 skip
2. `pnpm build:pools` 成功，三題的測資池產出且未超出位元組預算
3. 在瀏覽器實際提交三題的 `reference_solution`，每題得 20/20
4. 在瀏覽器實際提交三題各自的暴力解，**每題至少兩種拼法**——最直觀的逐行迴圈拼法，以及把工作推進 C 內建的最便宜拼法（A 題為整列切片指定、B 題為集合生成式、C 題為逐起點延伸中可用的任何 C 內建寫法）。每一種拼法的得分都必須落在 1/20 到 19/20 之間，且失敗的測資是階梯後段而非前段。每種拼法的實測得分與逐筆 ops 寫進量測記錄，spec 中一律以量測值敘述。**只量最直觀的拼法就宣稱斷崖成立，是本 change 第一版已經犯過並被推翻的錯誤。**
5. A 題的越界一致性：逐筆檢查 `testcase_plan` 的 20 筆 override，確認每一筆都滿足 `r_max + h_max − 1 ≤ R` 與 `c_max + w_max − 1 ≤ C`，檢查結果連同逐筆數值寫進量測記錄
6. B 題的最少教室數：以實測值記錄第 20 筆的教室數，並確認它落在情境可信的範圍（數十間而非數百間）。**不得以期望值代替實測值**——第一版即因把「平均同時使用數」誤當「最大同時使用數」而在規格中寫下錯誤數字
7. 三張說明圖在題目頁的實際欄寬下可讀：以瀏覽器量測圖片的顯示寬度，並確認最小字級在螢幕上不低於 12 px
8. 三題的題面範例與 `testcase_plan` 第 1 筆的 `literal` 逐字相同

**範圍邊界**：

- 在範圍內：三個題目頁、三支說明圖腳本、三張圖檔、本 change 的 spec 與量測記錄
- 在範圍外：測資引擎（Rust crate）、判題器、既有題目頁、教學文章、release

## Risks / Trade-offs

- **A 題的越界一致性規則被後續維護破壞，且守門測試不會叫** → 列為獨立驗收條件（第 5 項），逐筆數值寫進量測記錄，並在 spec 中以規範句寫死，讓後續任何調整都必須重跑該檢查
- **B 題不強迫 `heapq`，與需求討論時的預期不符** → 已在〈Decisions〉記錄完整算式與被否決的做法，避免後續維護者為了讓 `heapq` 變成必要而把 K 調到情境不合理的數量級；教學價值改由「排序後只維護教室狀態」承擔
- **C 題的斷崖依賴隨機值域的統計性質** → 從任一起點的延伸長度是期望值，個別測資會浮動；驗收條件第 4 項要求實測暴力解得分並以量測值敘述，不以理論值寫進 spec
- **運算計數器對 C 內建是瞎的，未來新題會再踩同一個坑** → 已升級為一條全域設計規則（見〈運算計數器對 C 層的工作是瞎的〉），驗收條件第 4 項強制每題量兩種拼法。這條坑的成本是本 change 第一版三題有兩題的斷崖是假的
- **A 題兩種拼法的死亡門檻不同，階梯中段有一段「巢狀死、切片活」** → 無法消除。階梯頂端兩者都死，兩者得分都落在部分分區間，兩者都要記進量測記錄；不得只記其中一種
- **判題的兩道閘門（一千萬運算、5000 ms）誰先觸發，隨拼法與 Pyodide 的相對速度而變** → 不在 spec 中斷言哪一道是 binding gate，改為由瀏覽器量測記錄實際的 verdict 與逐筆耗時
- **三題的暴力解得分需要實機量測，成本高** → 接受。前例 apcs015 與 gem-blast 都證明只靠本機投影會失真（本機把 deadline 套在逐筆時間上得到的分數與瀏覽器不一致），因此驗收條件明訂在瀏覽器量測
- **三張說明圖的工程量是本 change 最大的單一成本** → 沿用既有管線與既有的欄寬、字級結論，不重新推導設計參數
- **本機沒有 python3 時 `content-regression` 會 skip，可能讓 `reference_solution` 的錯誤溜過** → 驗收條件第 1 項明訂該測試必須確實執行，不得以 skip 當作通過
