## 二、根因

### 根因 1：平台事實漏帳——已知的教訓沒有被帶進矩陣

C3（每筆 5,000 ms 軟旗標）在本 change 初版被寫成「命中即判 TLE」的有效閘門，並據此設計了殺手帶的步數下限。實際上它對同步 Python 永遠不會觸發——**這件事在專案 memory 的 gem-blast RCA 早已記載**。矩陣的 C 表是從原始碼讀出來的，卻沒有與既有 RCA／memory 對帳，於是同一個坑踩了第二次，還連帶產生一個沒有作用的常數（`KILL_STEP_MIN`）與一段錯誤的殺手帶設計。

### 根因 2：「加保證」的修法會縮小資料空間，縮到底就塌縮成可猜函數

R1 為了封殺退化，加了「大球數測試逐條非退化」三條斷言。在週期 4（D=3）之下，這三條把 4 個殘值砍到只剩 2 個——而 2 個殘值必然可由「球號的奇偶」分開。**修法本身把答案變成了一個兩行就能寫出來的函數**。同一個機制在 apcs013 也出現：R2 為了封殺深度啟發式而加入固定形狀家族的深形狀，反而餵大了 R3 的形狀辨識器。

缺的是一道檢查：每次新增「逐條排除」類斷言後，必須計算**剩餘可用值域的資訊量**，確認答案沒有塌縮成低維函數。

### 根因 3：斷言牆守的是「路線清單」，而攻擊者用的是「路線家族」

三輪抓到的 hole 幾乎都是同一族的不同參數：`固定模數 M` 這一族，R1 抓到 M=8、R2 抓到 M=512、R3 抓到「M 任意但門檻可調」。每一輪都只把當時那個實例釘進 CAPS，下一輪就換個參數再穿一次。直到 R3 才把它改成「門檻 × 模數」的全掃描，並用**健全性**（模數是否為它套用到之每行週期的倍數）取代數字比較。apcs013 的「不逐組讀標記」家族也是同樣的軌跡：位置鍵 → 大小名次鍵 → 深度啟發式 → 形狀辨識器。

### 根因 4：成本軸一開始沒有機械閘門

`plan013.py`／`plan014.py` 只能看到「輸出對不對」，看不到 op 上限與牆鐘。前兩輪的成本結論全靠人工跑 probe，於是「逐球模擬 = 12/20」這種契約長時間沒有機械守門。`cost_gate.mjs` 到 R1 才補上，R2 才修正它自己也模擬了一道不存在的閘門（C3）。

### 根因 5：文件數字是手抄的，於是 disposition 會宣稱一個沒發生的修正

R2 的裁決表寫「常數與文件一起改為 70M」，實際上只改了文件；程式常數留在 85M 直到 R3。資料每改一次，A0／A8／V 表的數字就全部過期，而它們散落在四份文件裡靠人工同步。

## 三、改善清單（下一個 change 採用，接續 I-1～I-8）

- **I-9 平台事實對帳**：矩陣 C 表的每一列，除了指向原始碼，還必須對照既有 memory／RCA 檔逐條確認「這個機制上次被驗證時是什麼結論」。C3 就是漏帳的直接後果。
- **I-10 縮空間後的可猜性檢查**：任何「逐條排除」類斷言加入後，機械計算剩餘可用值域，並驗證答案不可由任何低維函數（小模數、奇偶、常數）決定。判準是**剩餘殘值數與可分離性**，不是「看起來還有很多選擇」。
- **I-11 路線家族化**：斷言對象一律定義為**參數化家族**並全掃描（門檻 × 模數、特徵鍵 × 規則、形狀庫成員），禁止只把當輪抓到的單一實例釘進 CAPS。
- **I-12 成本閘與斷言牆並列**：成本軸的契約從第一天就要有 `cost_gate`，且該閘門只能模擬**實測有效**的引擎機制（本次教訓：不要模擬 C3）。
- **I-13 文件數字單一來源**：文件中的量測數字改為引用 report JSON 的鍵，或加一支 doc-sync 檢查腳本比對「文件數字 vs report／常數」；裁決表宣稱的修正必須有對應的程式 diff 才能標記完成。
- **I-14 策展指紋即攻擊面**：資料生成用的形狀／參數家族本身是可被重建的指紋。凡是「答案取決於結構」的題目，承擔鑑別責任的資料一律用 **seed 驅動**家族生成，不用固定家族。
