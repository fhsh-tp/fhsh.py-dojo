# Handoff 稽核根因分析（2 輪未歸零）

> 對象：`.spectra/handoffs/stack-tree-batch-change-c.md`（change C 的接手手冊）
> 流程：2 輪 multi-sonnet 對抗稽核（R1 5 lens／15 條原始發現／10 條確認；R2 5 lens／9 條原始發現／6 條確認）→ 未歸零 → 3 個 opus 子代理獨立分析＋1 個 opus 合成。
> 本報告與 `rca-convergence-report.md`（change C 出題流程的 RCA）互補：那份談**被審物**（測資與數字），這份談**審查裝置本身**。

## 一、兩輪抓到什麼

**R1（6 條相異缺陷）**：抵達檢查用字典序排 id（回 `py054` 而非 `apcs014`）；archive 後 `assemble.py` 以固定四層 `..` 定位 repo 根而崩潰；e2e 指向 session scratchpad 的腳本；稽核輪條目數與所引用的裁決表不符；路線檔數量差一；四條平台殘餘的影響範圍宣稱有一條不成立。

**R2（4 條相異缺陷）**：**R1 的所有修正只存在於工作目錄，branch 尖端仍是壞版本**（critical）；R1 內嵌的 e2e 腳本呼叫不存在的 `agent-browser keyboard press`，錯誤被 `2>/dev/null` 吞掉；全 literal 題目清單錯；PR 步驟漏了 `git push`。

R2 的四條中有三條長在 R1 修復所觸及的表面上。

## 二、根因（3 個獨立分析合成後 6 條）

### RC-1 驗證通道＝作者的活體工作樹，交付通道卻是 tip／clone

文件第 4 行自己宣告讀者座標系（「無其他記憶的接手 agent」），但每一句都是從作者的活體 session 讀出來的：scratchpad 裡真的有那支腳本、修正真的在工作樹裡。R1 的驗證也在同一棵樹裡跑指令當 oracle——`python3 assemble.py` 會過，因為修好的檔案就在樹裡。凡是「作者樹有、交付物沒有」的差集，執行式驗證**在結構上偵測不到**；R1 只抓到其中留有字面痕跡的那一條（scratchpad 路徑字串），沒有字串可勾的（未 commit、未 push）全數漏掉。

**與舊 RCA 的關係**：全新。I-1～I-14 全部落在「題目內容／測資／數字」層，沒有任何一條談稽核自身的執行環境。失效點在審查裝置，不在被審物。

### RC-2 「完成」止於檔案編輯，未及會被交付的物件

三段疊加：(a) 受審主體被 gitignore、文件自陳「不會被 commit」，對它而言存檔＝出貨，這個判準外溢到同輪順手改的三個 tracked 檔；(b) `tasks.md` 的驗收在 5.4 就結束，之後的兩次寫入——archive 搬移（路徑深度 +1，當場弄壞 `assemble.py`）與稽核修復——沒有任何閘門涵蓋；(c) 文件的自檢斷言不具鑑別力：branch 名、tip hash、目錄存在性在「陳舊 tip 的乾淨 clone」與「髒工作樹」兩種狀態下都成立，唯一有鑑別力的 `git status --short` 在稽核期間**必定**是髒的，訊號在最需要它的時刻被結構性噤聲。

**與舊 RCA 的關係**：I-13 第二子句（「裁決宣稱的修正必須有對應的程式 diff」）幾乎命中，但作用域錯一級——它修的是動詞（要有 diff），沒修名詞（diff 要落在哪個物件上）；工作樹裡的未 commit 修改**字面上滿足**它。

### RC-3 稽核單位是「句子的真偽」，不是「程序的閉合」

兩輪 lens 都以文件已寫下的斷言為列舉單位，**缺失步驟不在分母裡**。`gh pr create` 的前置條件（branch 存在於 remote）沒有任何步驟建立，而建立它所需的事實就寫在同一份文件的上一節——事實與程序分放兩節、各自正確，交叉處無人負責。同一個分母問題也解釋嚴重度倒掛：注意力依「離受審文件多近」分配，風險卻依「離交付物多近」分配。

附帶指紋：`§0` 抵達區塊是跨 handoff 沿用的儀式模板，既有的 `deque-min-max-challenge.md` 用的是數值排序，本次重新即興寫了一版而丟失該防護——「模板被抄寫而非被執行」。

### RC-4 每輪的修正是未經審查的新表面，且證據級工具把自己的錯誤靜音

R1 為修第 3 條而把腳本從 scratchpad **憑記憶搬運**進文件，寫下不存在的子命令。它能存活是三層同時成立：驗收訊號是整支腳本最後那行「得分：N / M」而非逐步 exit code；所有呼叫 `> /dev/null 2>&1`，唯一的失敗訊號被主動丟棄；兩題 `starter_code: ""` 讓全選步驟在語義上本來就是 no-op，壞版本與好版本逐 byte 相同。三層任一層拿掉都會當場暴露。後果不只該條——出貨階梯那張「瀏覽器逐條實測」表是用帶著隱性壞步驟的量測器產出的，結果碰巧有效但證據鏈無效。

### RC-5 不變量是「與引用來源一致」，但來源整體錯誤時該檢查必然通過；且修正只落在副本

SSOT → RCA → handoff 是三層人工抄寫，SSOT 自己就不自洽，下游忠實繼承。更嚴重的是修補方向：R2 靠執行枚舉指令取得地面真相，但修正只寫回 handoff 這份副本，被明白稱為 SSOT 的 `trace-matrix.md` 當時未改——**派生文件對、它自己宣告的真相來源錯，而後者才是會隨 PR 進 staging 的那一份**（本報告撰寫時已補修 C11／F18 並改為附枚舉指令）。

時序證據：I-13 寫定於 `3c517c0`，handoff 於 36 分鐘後完成並同時違反其兩個子句——因為改善清單把範圍寫成「下一個 change 採用」，而「正在寫的接手筆記」不是一個 change，自動落在綁定範圍外。

### RC-6 受審物在版本控制之外：沒有 commit 邊界、沒有 diff

`.spectra/` 被 gitignore，handoff 沒有任何歷史。三個後果連鎖：沒有 commit 這個動作，整輪的節奏就是「存檔＝完成」，並外溢到 tracked 檔（RC-2 的結構成因）；第二輪沒有 diff 可看，只能重讀全文，審查退化成「讀內容合不合理」而非「查這輪改動有沒有落地」；文件宣稱尖端 hash 卻沒有自身的 commit 可綁定，讀者驗了 hash 相符、內容卻可以完全不是那個 hash 的內容。

## 三、改善清單 H-1～H-6（依「防止的嚴重度 ÷ 採用成本」排序）

| ID | 改善 | 防止 | 可機械化 |
|----|------|------|----------|
| **H-1** | **每輪的結束閘改為機械檢查交付狀態**：`git status --porcelain` 為空、`git rev-parse --short HEAD` 等於文件宣稱的尖端、文件若提到 remote 則 `git ls-remote --heads origin <branch>` 與敘述一致。任一條不符即該輪未結束。並為「不屬於任何 active change 的附帶修改」定義收案動作（`/spectra-commit` 是 change-scoped，掛不上） | R2-A（critical）、R2-D；並把 I-13 從「要有 diff」升級為「diff 必須落在會被交付的物件上」 | 完全可（三行 shell，可掛 skill 收尾） |
| **H-2** | **交付級腳本禁止吞 stderr**，改 `\|\| { echo "FAILED: <cmd>"; exit 1; }`；文件中每個外部 CLI 子命令必須對照一次 `--help` 並留下日期註記 | R2-B 中可由執行分辨的那一半 | 完全可（`grep -n '2>/dev/null'` 即 lint） |
| **H-3** | **可執行性驗證一律在「文件宣稱的那個 commit」的乾淨 worktree 執行**，且 worktree 建在 repo 之外（否則驗證動作本身會弄髒它要驗的「工作樹乾淨」） | R1-2、R1-3、R2-A、R2-D 四條一次殺死——都是「作者樹有、tip 沒有」的差集缺陷 | 大部分可；需維護「需要 node_modules 而豁免」的清單 |
| **H-4** | **集合／計數類主張一律附可重跑的枚舉指令**；稽核時執行該指令取地面真相，不與來源文件比對；**修正必須同時落在副本與 SSOT**，裁決表的「落點」欄改為必填多值 | R1-4／5／6、R2-C，以及本案發現的「SSOT 未同步」殘留 | 半機械化（「含數量詞的句子須有配對枚舉指令」可 lint） |
| **H-5** | **`/spectra-archive` 增加一步**：搬移完成後從新路徑重跑該 change 的全部驗證指令，全綠才算完成；附帶 lint：curation 腳本不得以固定層數 `..` 定位 repo 根 | R1-2 這一整類永久 | 完全可（固定步驟＋一條 grep） |
| **H-6** | **把上一輪的修正 diff 列為下一輪的第一條 lens**，並每輪把 gitignored 的 handoff 快照進 `.spectra/snapshots/<round>/` | R2 四條中的三條（都長在 R1 修復觸及的表面上） | 快照與 diff 可機械化；新內容的三問 checklist 需判斷 |

另有兩條成本較高、列為候補：**負控（negative control）**——多步驟程序必須附一個已知會失敗的輸入且真的報成失敗（防 R2-B 中無法用執行分辨的那一半）；**程序段落改用狀態機閉合審查**（前置狀態→步驟→後置狀態，逐步檢查前置條件由誰建立）。

## 四、後設觀察

三份 RCA（rank-code-duo、change C、本篇）出現同一個模式：**教訓被寫成文字，但沒有變成閘門**。本次尤其明顯——I-13 寫定 36 分鐘後就被同一個作者違反，原因是它的綁定範圍寫成「下一個 change 採用」。因此 H 系列的每一條都標註了「可機械化」欄；不可機械化的條目應誠實記為「願望」而非「改善」。
