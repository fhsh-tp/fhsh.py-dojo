## ADDED Requirements

### Requirement: testcase_plan frontmatter declaration

The pool-spec envelope accepted by `pool_inputs_from_spec` SHALL accept an optional top-level `testcase_plan` field: a non-empty JSON array whose entries are either a band object `{"count": <positive integer>, "override": <object>}` (an empty or omitted `override` SHALL be accepted and treated as "no patch") or a literal object `{"literal": <non-empty string>}`. Any other entry shape, any unknown key inside an entry, an empty array, or a non-array value SHALL produce a descriptive parse error that includes the entry index. The reserved-key refusal from the previous engine version SHALL be removed.

#### Scenario: valid plan with bands and literal parses

- **WHEN** a spec declares `testcase_plan` with two band entries and one literal entry
- **THEN** parsing succeeds and the plan total is the sum of band counts plus the number of literal entries

##### Example: deque-style plan

- **GIVEN** params `t` (int 2..3) and group `cases` repeating `t` with `n` (int 1..4000) and `nums` (count from `n`)
- **WHEN** `testcase_plan` is `[{"count": 3, "override": {"cases": {"params": {"n": {"max": 20}}}}}, {"count": 2, "override": {"cases": {"params": {"n": {"min": 2500}}}}}]`
- **THEN** the plan total is 5 and generation succeeds

#### Scenario: malformed entry is refused with index

- **WHEN** `testcase_plan` contains `{"count": 0}` or `{"literal": ""}` or `{"count": 2, "literal": "x"}` or `{"bogus": 1}` at index 1
- **THEN** the engine returns a parse error whose message contains the entry index 1 and the reason

#### Scenario: empty plan array is refused

- **WHEN** `testcase_plan` is `[]`
- **THEN** the engine returns a parse error stating the plan must contain at least one entry

### Requirement: Band override merges into base params and is fully re-validated

A band `override` SHALL mirror the shape of the base `params` object as a partial patch: the engine SHALL deep-merge `override` into base `params` (recursing where both sides are JSON objects, replacing otherwise), and SHALL run the merged result through the same `parse_params_value` validation applied to base params. At every level of the merge, an `override` key that does not exist in the corresponding base object SHALL produce a parse error naming the offending key path.

#### Scenario: override tightens a nested bound

- **WHEN** a band override sets `cases.params.n.max` to 20 on a base where `n` is int 1..4000
- **THEN** that band generates inputs whose `n` values fall within 1..20 while other bands are unaffected

#### Scenario: override referencing unknown key fails

- **WHEN** a band override references `cases.params.m` but base params declare no `m`
- **THEN** parsing fails with an error naming the unknown key

#### Scenario: merged result violating validation fails

- **WHEN** a band override sets `n.min` to 5000 on a base where `n.max` is 4000
- **THEN** parsing fails with the same min/max validation error the base parser produces

### Requirement: Per-band and literal budget enforcement

When a `testcase_plan` is present, the engine SHALL estimate the worst-case input size for every band using that band's merged params, and SHALL check every literal entry's UTF-8 byte length, against the effective input budget. Any violation SHALL fail with an error identifying the offending plan entry index. The base-params-only estimate SHALL NOT be the sole budget gate for plan specs.

#### Scenario: oversized band is caught

- **WHEN** a band override raises `n.max` such that the merged worst-case estimate exceeds the effective budget
- **THEN** generation fails with a budget error that names the band's plan-entry index, even if the base params estimate fits the budget

#### Scenario: oversized literal is caught

- **WHEN** a literal entry's byte length exceeds the effective budget
- **THEN** generation fails with a budget error naming that entry's index

### Requirement: Plan-aware deterministic seeding

When `seed` is present and a `testcase_plan` is declared, the RNG seed SHALL be derived from the seed string, the serialized params content, and the serialized plan content, so that editing any band bound or literal reshuffles the pool. When no `testcase_plan` is declared, the seed derivation input SHALL remain byte-identical to the previous engine version, so that existing non-plan pools are reproduced byte-identically.

#### Scenario: editing plan reshuffles

- **WHEN** a band's `max` changes from 20 to 21 with the same seed
- **THEN** the generated input sequence changes

#### Scenario: non-plan specs keep their sequences

- **WHEN** a spec without `testcase_plan` is generated by the new engine version
- **THEN** the output is byte-identical to the previous engine version's output for the same spec

### Requirement: Blocked generation order and count contract

For plan specs, `pool_inputs_from_spec(spec, count)` SHALL require `count` to be a positive multiple of the plan total (sum of band counts plus number of literal entries), failing with an error containing both numbers otherwise. The output SHALL consist of `count / plan_total` consecutive blocks; within each block, inputs SHALL follow the plan entry declaration order, with each band contributing exactly its `count` inputs and each literal contributing its exact string.

#### Scenario: block order follows declaration

- **WHEN** a plan declares band A (count 3), band B (count 2), literal L and count is 12
- **THEN** the output is [A,A,A,B,B,L, A,A,A,B,B,L] with values drawn fresh per block, and every literal position contains exactly L

#### Scenario: non-multiple count refused

- **WHEN** plan total is 6 and count is 200
- **THEN** generation fails with an error containing 200 and 6

### Requirement: Mutual exclusion with testcase_count

A challenge SHALL NOT declare both `testcase_plan` and `testcase_count`. The build-time reader SHALL reject a frontmatter that declares both with an error naming the file. The engine envelope SHALL NOT accept a `testcase_count` key (it is not part of the pool spec; unknown-field rejection covers it).

#### Scenario: coexistence rejected at build time

- **WHEN** a challenge frontmatter declares both `testcase_plan` and `testcase_count`
- **THEN** the pool build fails with an error naming that challenge file

### Requirement: Dev-mode plan generation entry

A WASM entry `generate_dev_inputs(spec_json)` SHALL accept `{"params": {...}, "testcase_plan": [...]}` and return one full plan round (`{inputs: [...]}` with plan-total inputs) using entropy seeding, with inputs ordered by plan entry declaration order. A spec without `testcase_plan` SHALL be refused with a descriptive error. The same parse validation and per-band budget hard-cap rules as the pool entry SHALL apply.

#### Scenario: dev round matches plan shape

- **WHEN** the dev entry is called with a plan of band(3) + band(2) + literal
- **THEN** exactly 6 inputs are returned, positions 1-3 from band one's merged params, positions 4-5 from band two's, position 6 the literal string

#### Scenario: dev entry without plan is refused

- **WHEN** the dev entry is called with params only
- **THEN** it returns an error directing callers to `generate_challenge`
