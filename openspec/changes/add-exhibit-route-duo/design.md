## Context

批次 change C，兩題並置：apcs013「展場動線重建」（已知兩種打卡紀錄還原第三種）與 apcs014「彈珠台軌道預測」（不逐球模擬、由球號直推路徑）。所有量化事實見同目錄 `trace-matrix.md`（SSOT），本檔一律引用事實 ID，不重複來源數字。路線清單的機械正本是 `curation/plan013.py::CAPS` 與 `curation/plan014.py::CAPS`。

## Goals / Non-Goals

**Goals**

- 兩題各承擔一個互補的教學軸：apcs013＝語義鑑別（雙模式還原）、apcs014＝成本鑑別（球數斷崖）。
- 出貨資料可逐 byte 重現；策展腳本與量測 harness 隨 change 入庫。
- 題面零資料結構術語、零「不可能」句、零未實測數字。

**Non-Goals**

- 不為 apcs013 建 op 斷崖：C 層繞道實測不可獵殺（A3／A4）。
- 不獵殺 apcs014 的兩條收編路線（逐層計數 L1、取週期再模擬 P1，B8）。
- 不動判題引擎常數與計數方式（C1／C3／C4）。三項平台層性質本 change **不以測資規避、只記錄並建議另案處理**：tracer 只數 line 事件因而可被「同行攤平／K 球批次」稀釋（C2／C13）、`sys.settrace(None)` 可直接凍結計數（C12）、5,000 ms 軟旗標對同步碼不會觸發（C3）。三者對全站既有 op 斷崖題一體適用。
- 不處理 `testcase_plan` literal 進入生產 bundle 的既存殘餘（C11／F18），另案處理。

## D1 判題機制與預算

依 C1–C11。四項對本 change 有結構性影響：

1. C2 決定 apcs013 無法用成本軸鑑別（A3），也決定 apcs014 的 op 下界必須以「攤平寫法每球 1 op」計（B3）。
2. C6 決定 apcs013 出貨動線深度上限 300（A5）：測資不得把學生的正常遞迴解一起殺掉。
3. C3 無效＋C4／C4b 決定 apcs014 殺手筆只設**總步數上限**、不設下限：牆鐘軟旗標既然攔不到同步碼，堆高步數只會拖長陣亡提交的等待、逼近整場中斷的全綠誤呈現（B5b／B7）。
4. C11 決定「離線算答案」屬既存殘餘、不以測資調整規避（F18）。

## D2 語義與值域

**apcs013**：輸入首行 T；每組首行 `M n`，其後兩行各 n 個展區編號。模式 1 給甲＋乙求丙、模式 2 給乙＋丙求甲（A1）。展區編號為 1..n 的隨機重排（A7）。輸出每組一行、n 個編號以單一空白分隔。1 ≤ n ≤ 1500；動線深度 ≤ 300（A5）；每筆測資 ≤ 50,000 bytes、`input_budget: 63488`（A8）。輸入無二義性（A13）。

**apcs014**：輸入首行 T；其後 T 行各為 `D I`。機台共 D 層＝第 1..D−1 層翻板＋第 D 層 2^(D−1) 個袋子（B1）。2 ≤ D ≤ 20、1 ≤ I ≤ 10,000,000；**球數可超過袋數**，機台狀態以 2^(D−1) 為週期（B1b）——此值域是斷崖能否成立的關鍵，不是隨手訂的（B4）。每組輸出一行袋號。`input_budget` 沿用預設（B10）。

## D4 階梯哲學與收編清單

- **apcs013 階梯＝語義**：第 1–10 筆純模式 1；第 11 筆純模式 2（頁面第二範例）；**第 12–20 筆每筆 5 組、同時含兩種模式，且 9 筆的模式序列兩兩相異**——混合是「只讀一次模式標記」只能拿 11/20 的理由，序列互異則是「只讀第一個標記＋位置規則」上界 12/20 的理由（A16；若 9 筆共用同一種序列，該路線可拿 20/20）。第 1、11 筆為範例筆，明記豁免鑑別責任（A15）。
- **apcs014 階梯＝成本**：第 1–15 筆任何逐球寫法可過（總步數 ≤ 1M）；第 16–20 筆總球數 ≥ 20M（步數上限 55M），三種逐球寫法（一般／單行精簡／依 D 攤平單球）實測皆 15/20（B5／B6）。已知殘餘：K 球批次寫法與 `sys.settrace(None)` 可規避計數（B3b），屬平台層、不以測資規避。
- **收編清單**（語義正確、題面不得暗示其不可行）：apcs013 的 `.index()` C 層天真解（A3）與鏡射解 R1（A12）；apcs014 的逐層計數 L1 與取週期再模擬 P1（B8）。
